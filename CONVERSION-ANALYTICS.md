# Conversion tracking on Cloudflare Pages

Custom tracking ships disabled. Cloudflare Web Analytics continues to handle site-level traffic and performance. The custom endpoint has no read operation.

## Deployment and activation

1. Before merging, configure the Cloudflare Pages project `eirich-it-services` for Git-based builds. Keep the project root at the repository root so Pages discovers `functions/`. Set the build command to `python3 .github/scripts/build_pages.py` and the output directory to `dist`. Use Python 3.10 or newer. Coordinate the settings change with the first build of this branch since older commits do not contain the build script. Validate a preview that uses these settings before publishing production.
2. Keep `CONVERSION_ANALYTICS_ENABLED` unset in both environments for the initial deployment. Verify the existing **Production** Analytics Engine binding `ANALYTICS` targets `eirich_conversions`. Leave Preview without this binding or activation variable. The browser script is staged only for an enabled `main` build, and the endpoint requires both the canonical origin and the runtime activation variable. Preview URLs and `pages.dev` URLs cannot write, even if a binding is supplied.
3. Before a later activation, approve the German and English notices and update the passages describing the disabled state. Review the purpose, applicable legal basis or consent requirements, Cloudflare's processing terms, international transfer arrangements, access controls and operational log settings. Cookieless measurement alone does not resolve Swiss DSG or GDPR obligations. Cloudflare processes request metadata separately from the application dataset. Keep request body logging off.
4. After approval, set `CONVERSION_ANALYTICS_ENABLED=true` for **Production only**, as a Pages build and Functions runtime variable, then redeploy `main`. Keep the existing Web Analytics setting. No new API token is needed. If available under the current plan, configure a Cloudflare rate-limit rule scoped to `POST /api/analytics` and inspect Analytics Engine usage after activation.

The staging script copies the sitemap routes, shared static files, custom 404 page and current IndexNow verification file explicitly. Add any future static assets to the staging list and update the canonical route allowlist when routes change. The only Functions invocation route is `/api/analytics`.

## Collection and limits

The browser sends a fixed event over same-origin HTTPS using a non-blocking keepalive request with credentials omitted and referrer suppressed. Analytics respects browser Global Privacy Control and Do Not Track. The browser holds attribution in memory for the current document. Navigation can lose attribution, including a service-page link to the contact form. No cross-page attribution or identifier is created. Known external referrers map to source labels. Other external referrers map to `other_referral`. Duplicate query parameters and unknown UTM values are ignored.

Use the source allowlist in `analytics-schema.mjs`. Recognized media are `organic`, `referral`, `directory`, `social`, `maps`, `email` and `cpc`. Campaigns start with `zurich_it_support`, `local_directories` and `senior_it_help`. These are proposed tracking labels. Confirm campaign naming before launch and add reviewed labels to the shared allowlist. Keep personal information out of all UTM tags, including tags ignored by this feature, because URLs may reach infrastructure logs.

The endpoint validates the exact HTTPS origin, JSON content type, maximum 512-byte body and allowlisted fields. It allows one write per request and caps attempted writes at 120 per minute per isolate. The browser caps events at 20 per document. The isolate cap resets on isolate replacement and is neither an account-wide quota nor a substitute for edge rate limits. Origin and Fetch Metadata checks discourage browser cross-site submissions. Automated clients can forge those headers and submit valid-looking events. A burst can crowd out legitimate events, and delivery can also be lost when the browser closes or the network fails. Treat the counts as estimates.

Clicks measure contact intent. Form success means FormSubmit confirmed the submission. It does not confirm inbox delivery, a qualified lead, or a sale. Form errors and campaign landings provide context for the conversion counts.

## Dataset schema and retention

| Column | Value |
| --- | --- |
| `timestamp` | UTC ingestion time generated by Analytics Engine |
| `index1` | Constant `site` sampling index, never a visitor identifier |
| `blob1` | Event type |
| `blob2` | Canonical site path |
| `blob3` | Language, `de` or `en` |
| `blob4` | Allowed source or referral category |
| `blob5` | Allowed medium |
| `blob6` | Allowed campaign |

Empty attribution values are stored as empty strings. Cloudflare documents three months of [Analytics Engine retention](https://developers.cloudflare.com/analytics/analytics-engine/limits/#data-retention). The application does not record IP addresses, User-Agent, contact or form data, full URLs, arbitrary query strings, or identifiers. Review infrastructure logging separately. Access reports through authorized Cloudflare tooling and use existing approved access.

## SQL reports

The queries cover the last 30 days and weight every count by `_sample_interval` to account for Analytics Engine sampling. The conversion breakdowns include contact clicks and confirmed form submissions. The event breakdown also surfaces diagnostics.

```sql
-- Conversions by UTC day
SELECT toStartOfDay(timestamp) AS day, SUM(_sample_interval) AS events
FROM eirich_conversions
WHERE timestamp >= NOW() - INTERVAL '30' DAY
  AND blob1 IN ('phone_click', 'email_click', 'whatsapp_click', 'contact_form_success')
GROUP BY day ORDER BY day;

-- Events by type
SELECT blob1 AS event_type, SUM(_sample_interval) AS events
FROM eirich_conversions
WHERE timestamp >= NOW() - INTERVAL '30' DAY
GROUP BY event_type ORDER BY events DESC;

-- Conversions by service page, excluding the homepages
SELECT blob2 AS page_path, SUM(_sample_interval) AS events
FROM eirich_conversions
WHERE timestamp >= NOW() - INTERVAL '30' DAY
  AND blob1 IN ('phone_click', 'email_click', 'whatsapp_click', 'contact_form_success')
  AND blob2 NOT IN ('/', '/en/')
GROUP BY page_path ORDER BY events DESC;

-- Conversions by language
SELECT blob3 AS language, SUM(_sample_interval) AS events
FROM eirich_conversions
WHERE timestamp >= NOW() - INTERVAL '30' DAY
  AND blob1 IN ('phone_click', 'email_click', 'whatsapp_click', 'contact_form_success')
GROUP BY language ORDER BY events DESC;

-- Conversions by traffic source, including unattributed rows (empty source)
SELECT blob4 AS source, SUM(_sample_interval) AS events
FROM eirich_conversions
WHERE timestamp >= NOW() - INTERVAL '30' DAY
  AND blob1 IN ('phone_click', 'email_click', 'whatsapp_click', 'contact_form_success')
GROUP BY source ORDER BY events DESC;

-- Conversions by recognized UTM campaign
SELECT blob6 AS campaign, SUM(_sample_interval) AS events
FROM eirich_conversions
WHERE timestamp >= NOW() - INTERVAL '30' DAY
  AND blob1 IN ('phone_click', 'email_click', 'whatsapp_click', 'contact_form_success')
  AND blob6 != ''
GROUP BY campaign ORDER BY events DESC;

-- Daily contact form outcomes
SELECT toStartOfDay(timestamp) AS day, blob1 AS outcome, SUM(_sample_interval) AS events
FROM eirich_conversions
WHERE timestamp >= NOW() - INTERVAL '30' DAY
  AND blob1 IN ('contact_form_success', 'contact_form_error')
GROUP BY day, outcome ORDER BY day, outcome;
```

## Verification and rollback

- With Node.js 24 and Python 3.10 or newer, run `node --test .github/scripts/test_analytics.mjs`, `PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s .github/scripts -v` and `python3 .github/scripts/build_pages.py`.
- In a deployed preview and in the initial disabled production deployment, check both languages, the calculator, menu and contact links. Verify that the HTML contains no custom analytics loader, and an otherwise valid analytics POST produces no dataset row. Confirm the sitemap, robots file and verification key return 200, an unknown path returns the custom page with HTTP 404, canonical redirect behavior still matches production and Cloudflare Web Analytics still reports traffic. Check that URLs for repository source, tests and configuration outside the public allowlist return 404.
- After a separately approved activation, open a service page tagged with `?utm_source=google&utm_medium=organic&utm_campaign=zurich_it_support`. Check for one 204 landing event and one per intentional contact click. Check that a test enquiry produces one success only after FormSubmit confirms it. Block the FormSubmit request to verify the error outcome and UI. With a browser that sends GPC or DNT, verify that there are no custom analytics POSTs. Compare the SQL results with the test actions. Check the real site for script MIME types, navigation behavior, rendering and performance.
- To stop collection, unset the Production activation variable and redeploy. Verify the loader disappears and valid POSTs return 404. For an urgent stop before redeployment completes, block `/api/analytics` at the edge if available. Existing rows age out under Analytics Engine retention. To roll back application changes, redeploy a known-good build or revert the commit and coordinate the build settings if the restored version predates the staging script.
